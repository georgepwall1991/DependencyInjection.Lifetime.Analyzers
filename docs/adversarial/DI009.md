## Contract before implementation

### Shapes that MUST report

| ID | Shape | Test evidence |
| --- | --- | --- |
| R1 | A singleton open-generic implementation has a uniquely selected constructor that resolves a known scoped or transient dependency through a direct or keyed registration. | Existing DI009 direct, keyed, descriptor, and greedy-constructor tests in `DI009_OpenGenericLifetimeMismatchAnalyzerTests`. |
| R2 | A supported lifetime-changing code fix rewrites direct `Add*Singleton`/`TryAdd*Singleton`, keyed equivalents, or inline `ServiceDescriptor` singleton registrations without changing unrelated syntax. | Existing `DI009_OpenGenericLifetimeMismatchCodeFixTests` direct/keyed/descriptor cases. |

### Shapes that MUST stay quiet

| ID | Shape | Test evidence |
| --- | --- | --- |
| Q1 | An open-generic implementation's constructor dependency registration has generic constraints that cannot overlap with the consumer's service type parameter constraints; no closed runtime construction can capture the dependency. | `OpenGenericWithIncompatibleDirectConstraints_NoDiagnostic`. |
| Q2 | A keyed singleton/dependency pair uses an unknown runtime key expression, even when both unknown expressions are represented by the same syntax-independent value internally; key equality is not proven. | `UnknownKeyExpressions_AreNotAssumedEqual_NoDiagnostic`. |
| Q3 | Non-singleton, closed/non-generic, factory-backed, ambiguous-constructor, unknown-lifetime, and unregistered paths remain quiet unless the existing analyzer can prove the captive relationship. | Existing DI009 quiet/unsupported tests. |

### Deliberately unproven and therefore silent

These boundaries are intentionally not widened in this pass:

- keyed registration expressions whose runtime equality cannot be proven (except `KeyedService.AnyKey`, which is an explicit framework sentinel);
- factory-backed open generics and arbitrary factory capture (DI003 owns its high-confidence factory analysis);
- conditional service-collection reachability and independent composition-root flow partitioning;
- `DescribeKeyed`/descriptor collection forms and fixer rewrites not already supported by the analyzer/fixer contract;
- implementation projection compatibility, abstract/non-instantiable implementation validity, and invalid constructor graphs owned by DI013/DI018/DI015.

## Opposition review

1. **“Treat every unknown key as equal so a possible captive dependency is not missed.”** That creates false positives: two runtime key factories can produce distinct objects, and the analyzer cannot prove equality. Unknown keys therefore match neither each other nor a concrete key; only an explicit `AnyKey` fallback can establish a relationship.
2. **“Report the direct constrained generic case because the open registration has the right arity.”** Arity is insufficient. If the consumer requires `struct` and the dependency implementation requires `class`, no valid closed construction exists. DI009 must not report a lifetime mismatch for an impossible graph; DI013/DI015 can own invalid registrations.
3. **“Expand DI009 to every descriptor/factory/branch shape while touching these helpers.”** That would widen beyond tested ownership and risk duplicate or speculative diagnostics. The existing unsupported shapes remain silent until independently proven and pinned.
4. **“Make the fixer rewrite every diagnostic.”** A fixer must not offer a no-op or rewrite an unsupported descriptor/flow form. It remains limited to the existing safe registration syntax in this pass.

## Resulting contract for this pass

Harden only the two proven false-positive families above. Preserve existing report coverage and conservative silence for every deliberately unproven case. A mutation that merely broadens unknown-key or impossible-constraint reporting is not a reason to widen the rule.
