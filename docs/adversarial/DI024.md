# DI024 adversarial contract — hosted-service scope creation outside the loop

## Baseline recorded before implementation

Stryker.NET 4.16.0 (`Release`, `Basic`, per-test coverage) was run against `DI024_HostedServiceScopePerIterationAnalyzer.cs` with the 99-test `DI024_HostedServiceScopePerIterationAnalyzerTests` filter. DI024 intentionally has no code-fix provider, so its fixer baseline is **N/A**.

The targeted analyzer baseline was **66.33%**. After the exact `System.Threading.PeriodicTimer` loop gate and fake-timer regression, the analyzer rerun scored **66.34%**, above baseline. DI024 remains fixerless by design.

## Contract before implementation

### Shapes that MUST report

- A hosted `BackgroundService.ExecuteAsync`, `IHostedService`/lifecycle execution entry point, or documented one-hop same-type helper creates an `IServiceScope`/async scope once before an unbounded cancellation, `while(true)`, `for(;;)`, periodic-timer, channel-consumer, or equivalent long-running loop and uses that scope or a service resolved from it in the loop.
- The report includes direct scope use, a provider alias, opaque scope use, or a service proven scoped by the registration model. Generic and supported direct-`typeof`, keyed compile-time requests, casts/null-forgiving wrappers, and declared-then-assigned try/finally scope locals participate where existing tests prove them.
- Scope creation in a field initializer/constructor or hosted execution method is reported when the hosted entry point demonstrably reuses it across iterations. Scope creation outside the loop is still a correctness issue even if the current use is not a service resolution.

Existing evidence includes the direct `using`/`CreateScope` tests, `BackgroundService`/hosted lifecycle tests, channel/periodic-loop tests, helper tests, alias tests, and scoped-service tier tests in `DI024_HostedServiceScopePerIterationAnalyzerTests`.

### Shapes that MUST stay quiet

- Scope creation inside each loop iteration; use only before the loop; bounded `for`/plain `foreach`/ordinary async iteration; non-hosted classes and stop/stopping/stopped callbacks.
- All-singleton services resolved from a hoisted scope, unknown/runtime service types, dynamic keys, same-named user resolution methods, provider aliases repointed inside the loop, and services whose lifetime cannot be proven.
- Scope/helper flow through unsupported fields/parameters, cross-declaration helpers, uncalled/deferred/transitive helpers, or concrete custom provider/factory implementations remains unproven and quiet.

### Deliberately unproven and therefore silent

- `??=`, embedded `using (scope = ...)`, `as`/conditional/coalesce/task-wrapped scope creation, service assignment after declaration, provider alias chains/casts/postfix wrappers, property/field provider flow, explicit interface implementations not textually recognized as hosted entry points, and unusual cancellation-condition comparisons.
- Any automatic fixer: moving a declaration into a loop changes disposal, capture, exception, nested-loop, and async-disposal semantics and therefore remains a manual repair.

## Opposition review

1. **“Any method named `ExecuteAsync` or `WaitForNextTickAsync` is a hosted loop.”** Names and fake timer APIs are not framework proof. The detector must retain its exact hosted/scope boundaries and should not widen to arbitrary user types.
2. **“A textual pre-loop field assignment dominates every loop.”** Conditional/exceptional field creation and reassignment can leave a loop reusing an old or null scope. Without CFG/dominance proof, do not widen field flow; preserve the current conservative contract and pin known guardrails.
3. **“Any assignment inside a loop means per-iteration replacement.”** A conditional or unreachable reassignment can leave the old scope live on another path; suppressing solely from lexical assignment is conservative and must be documented rather than treated as proof.
4. **“Scan nested lambdas/local functions as loop execution.”** Deferred or never-called bodies do not prove a loop use. Keep unsupported deferred control flow silent unless invocation and lifetime are proven.
5. **“Ambient known-scoped registrations always win.”** Explicit effective registrations, including singleton overrides and keyed wildcard matches, must determine service tier; unknown/path-dependent registrations remain silent.

## Resulting contract for this pass

Keep DI024 fixerless. Harden only a demonstrated high-confidence false positive/negative with a focused regression test; do not broaden syntactic loop or helper inference. The intentional manual-repair boundary and unproven shapes above remain unchanged.
