## Contract before implementation

### Shapes that MUST report

| ID | Shape | Test evidence |
| --- | --- | --- |
| R1 | A DI-activated normal service constructor injects `IServiceProvider`, `IServiceScopeFactory` (when the service is not singleton), or `IKeyedServiceProvider`. | Existing `Constructor_WithIServiceProvider_ReportsDiagnostic`, `Constructor_WithIServiceScopeFactory_ReportsDiagnostic`, and `Constructor_WithIKeyedServiceProvider_ReportsDiagnostic`. |
| R2 | Constructor selection, open-generic activation, and effective registration replay determine whether the provider-injecting constructor is actually activatable. | Existing greedy/open-generic and effective-registration DI011 tests. |

### Shapes that MUST stay quiet

| ID | Shape | Test evidence |
| --- | --- | --- |
| Q1 | An abstract/non-instantiable implementation is registered with a provider-injecting constructor; no MEDI activation can occur and DI018 owns the invalid registration. | `AbstractImplementation_WithIServiceProvider_NoDiagnostic`. |
| Q2 | Factory-backed or instance-backed registrations, factory-style classes, real middleware, hosted services, endpoint filter factories, singleton scope-factory injection, non-public constructors, and unregistered services remain within the documented exceptions. | Existing DI011 allowed-case tests. |
| Q3 | A registration removed by a proven effective-registration replay is silent, while conditional/bypassable removal remains conservative. | Existing `RegisteredService_RemovedByRemoveAll_NoDiagnostic`, `RegisteredService_RemovedByClear_NoDiagnostic`, and replay tests. |

### Deliberately unproven and therefore silent

These boundaries remain unchanged in this pass:

- arbitrary factories whose body would require separate data-flow analysis;
- provider-like custom interfaces or user-defined conversions that are not the bound MEDI abstractions;
- runtime reachability beyond the existing service-collection replay model;
- provider injection through fields, properties, method bodies, or `IEnumerable<IServiceProvider>` rather than a selected constructor parameter.

## Opposition review

1. **“Report provider injection even on abstract implementations because the base constructor still uses a provider.”** The registered abstract implementation cannot be activated by MEDI. Reporting DI011 alongside the DI018 invalid-registration diagnostic adds noise without a proven runtime misuse; the guard keeps the analyzer local to activatable registrations.
2. **“Silence every type named `Factory`, middleware, or hosted service.”** Names alone are not proof. The existing implementation requires value-returning factory members or bound framework interfaces; ordinary `CacheFactory`/non-middleware `Invoke` shapes remain reportable.
3. **“Treat factory delegates as constructor activation.”** Factory-backed registrations bypass constructor activation and are intentionally outside DI011; DI003 owns high-confidence factory capture analysis.
4. **“Broaden provider detection to custom provider-like abstractions.”** That would report types whose runtime ownership is not proven to be MEDI's provider surface. The analyzer remains bound to `WellKnownTypes` symbols.

## Resulting contract for this pass

Harden DI011 only by suppressing the confirmed abstract/non-instantiable-registration false positive. Preserve all existing report coverage and conservative exceptions; do not add a fixer or speculative provider-like detection.
